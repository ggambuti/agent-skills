# Headless agent status report

Synthesize a complete, evidence-based status report on the headless
agent running in this project, from the state the loop already
maintains. One gathering pass, then synthesis — no live experiments.

## Hard rules

1. **Strictly read-only.** Never checkout the work branch, commit,
   edit any state file (`GOAL.md`, `PHASE`, `PROGRESS.md`,
   `ATTENTION.md`, `BLOCKED.md`, `HANDOVER.md`), or create `STOP`.
   Never run the verification command or builds — they can collide
   with the agent's own mid-cycle runs. Reporting must be invisible to
   the loop.
2. **Evidence only.** Every claim in the report cites what it comes
   from (a PROGRESS.md entry, a commit, a heartbeat line, an .err
   tail). If something cannot be determined from the gathered data,
   say "cannot determine" — never infer silently. Do not mark
   Definition-of-Done items complete unless the evidence shows it;
   PHASE=HARDENING is the agent's own claim, so cross-check it against
   commits/tests before repeating it as fact.
3. **Escalations first.** Anything in `ATTENTION.md` and any auth
   errors outrank everything else — they are the items only the user
   can fix, and the reason they asked for a report.

## Procedure

1. **Locate the installation.** The repo root must contain
   `HANDOVER.md` (regenerated by the loop at every launch — it carries
   the branch, kit directory, model, and platform-correct commands).
   If it is missing here, ask the user for the repo path rather than
   guessing; if `GOAL.md`/`PHASE` exist but `HANDOVER.md` does not,
   the loop has never launched — report that.

2. **Gather once.** Run this skill's `assets/gather.sh <repo>`
   (read-only; parses HANDOVER.md for branch/kit/model itself). It
   emits delimited sections: CONFIG, SERVICE, HEARTBEAT, PHASE, STOP,
   GOAL, PROGRESS (tail + first entry), ATTENTION, BLOCKED, GIT
   SUMMARY (commit counts, WIP-checkpoints, last-commit time,
   diffstat), RECENT CYCLE ERRORS, USAGE (per-day table + per-model
   breakdown). If gather.sh is unavailable, run its steps manually —
   keeping every one read-only.

3. **Diagnose the headline state** from the evidence, in this order:
   - `ATTENTION.md` has open items, or .err files show auth errors
     ("OAuth", "authentication", "401") → **NEEDS YOU** (auth outranks
     everything: the loop polls forever and cannot fix it).
   - Service not running and no STOP file → **DOWN** (crashed harder
     than the supervisor could handle, or never installed — rare;
     check heartbeat tail).
   - STOP file present → **STOPPED BY USER** (report what it achieved).
   - Heartbeat shows repeated "sleeping ... retrying forever" and .err
     shows rate-limit/overload/network errors → **WAITING ON
     QUOTA/OUTAGE** (self-resolving; say since when, from timestamps).
   - Heartbeat shows rising "stuck=N" with no commits → **STRUGGLING**
     (loop never halts, but flag what it keeps failing at, from
     PROGRESS.md).
   - Otherwise → **WORKING (BUILDING)** or **HARDENING** per PHASE.
   Compare the last commit timestamp with the current time and say the
   gap explicitly ("last commit 40 min ago" reads very differently
   from "3 days ago").

4. **Write the report** in this structure, concise but complete:
   - **Headline**: one line — state + one-sentence justification.
   - **Needs you**: ATTENTION.md items and auth problems, each with
     the fix (auth fix commands are on HANDOVER.md). Omit the section
     header only if truly empty.
   - **Goal progress**: each Definition-of-Done item with a
     status (done / in progress / not started) and one piece of
     evidence (commit, test, PROGRESS entry). Note the BUILDING →
     HARDENING transition date if it happened, and what hardening has
     covered since.
   - **Work summary**: commits since base (count, diffstat headline),
     the 3–5 most significant changes in plain language, number of
     WIP-CHECKPOINT commits (unverified — flag for review).
   - **Blockers**: BLOCKED.md items, each with how long it has been
     parked (from its dated entry).
   - **Health & consumption**: uptime since first PROGRESS entry,
     failed-vs-successful cycle counts and what the failures were
     (quota / outage / other, from .err), the usage table's trend
     (tokens and notional cost per day — flag if per-cycle cost is
     drifting upward, which usually means PROGRESS.md growth), and the
     per-model breakdown (is the orchestrator/subagent tiering
     behaving).
   - **Suggested actions**: at most 3, only if warranted (e.g. "answer
     ATTENTION item 2 in-band", "consider a GOAL.md amendment for X",
     "auth needs setup-token"). Never suggest stopping unless the user
     asked about stopping.

5. **Tone and length.** This is a briefing for the project owner
   returning to their desk (or reading from a beach): lead with what
   they must act on, keep the whole report under a screen and a half,
   use their project's own terminology from GOAL.md, and prefer plain
   statements over tables except for DoD status and usage numbers.

## Relationship to the headless-agent skill

This skill only reads what that skill's loop maintains. If the user
asks to CHANGE anything after the report (adjust the goal, answer an
ATTENTION item, change model, stop), the procedures live on the repo's
`HANDOVER.md` and in the headless-agent skill: goal edits are hot
(edit GOAL.md + commit; reset PHASE to BUILDING if expanding a
satisfied Definition of Done), behavior/model changes need
STOP → reinstall. Answering ATTENTION items in-band = append an
`ANSWER (date): ...` line under the item in ATTENTION.md — this is
the one write the user may direct you to make, and it is theirs, not
the loop's.
